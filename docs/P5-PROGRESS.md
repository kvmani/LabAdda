## Referenced-file inspection slice

Schema 0008 adds operator-only non-destructive inspection receipts. `labadda inspect-storage` has file/byte limits and cooperative scan-time checks, fixed selected metadata rows, size/hash verification for originals, separate readable-preview bytes and capped diagnostic samples. Missing, modified, unsafe or unavailable files produce explicit issue codes; budget exhaustion remains partial. It does not enumerate orphan files, repair counters, delete blobs or authorize enforcement. A live scan can race changes; previews have no stored expected integrity digest, so their integrity remains unverified. The scan time budget cannot bound blocking filesystem/database I/O. Interrupted running receipts remain visibly unfinished rather than success.

The admin web view lists these receipts without private filenames or content; the CLI runs only under trusted host-operator access. Full validation passed **207 backend tests**, real PostgreSQL recovery, no migration drift, **11 frontend tests**, typecheck and build. The root/prefix governance scenario passed 18 browser checks, and two additional browser checks confirmed actual CLI receipts in the admin view. Review corrected sample timestamps to actual observation time, the displayed-five/history-twenty count, preview-verification labels and unknown running counters. Read-only measurements remain unsuitable as a complete enforcement ledger.


## Narrow operational observer capability

Schema 0009 adds expiring `usage.read` grants. An admin must confirm the current password and provide a reason for each grant/revoke; grants last at most 720 hours. The normal user sees `/operations` only when authorized. This provides read-only storage metadata and never changes `is_admin` or content grants. Identity/policy/sample-write/audit/private-note/file access remain denied. API tests cover password failure without secret audit, expiry, revoke, invalid bounds, CSRF, a concurrent grant/identity update, and visibility beyond a capped list. The user authority lock uses PostgreSQL NO KEY UPDATE so role/password changes stay serialized while foreign-key audit checks do not deadlock. A selected-account revoke action remains available independently of listed rows.

Twelve browser checks at root/prefix cover denied → wrong confirmation → explicit read grant → administration refused → revoke → refreshed data removed. Password fields clear after each attempted server operation. Restored backups clear copied reader grants, and the real recovery test proves that fresh login does not restore the delegated privilege. The general role/capability, approval, policy activation and full accounting contracts remain incomplete.

During validation, two local pytest processes initially collided while resetting the same disposable database; those runs were discarded. The subsequent full suite was run serially; browser tests use separate e2e databases. Do not run multiple pytest processes against the same LABADDA_TEST_DATABASE_URL.

Final capability-slice validation: **214 backend tests**, real recovery and migration-drift checks, **11 frontend tests** and production build passed in a serial run. Eighteen governance plus twelve capability browser checks passed at root/prefix; earlier operator-receipt checks also passed. Development/research instances were migrated to schema 0009 and restarted while preserving their content; authenticated usage/delegation requests and readiness passed on both. Screenshots include the observer's metadata-only view. Hosted CI completion is not claimed.

## Pending original-byte reservations

Schema 0010 adds durable pending reservations for the existing environment-controlled upload allowance. Measured bytes reserve before storage, then atomically become Asset bytes; expiry/revocation checks precede commit. The user sees pending originals separately. Ten upload-admission tests cover parallel oversubscription, invalid input, stale/expiring reservations, lost sessions, definite pre-commit rollback, successful commits with lost replies, unknown outcomes, partial preview writes and no-clobber storage collisions. Filesystem and DB work run in a worker thread; current identity locking is shared with governance without granting administration rights.

Validation: full serial suite **224 backend tests**, real PostgreSQL recovery/drift checks, **11 frontend tests**, production build, 18 governance and 12 delegation browser checks passed. Recovery now verifies copied pending capacity is cleared alongside operational grants. These are upload-versus-upload guarantees only: board-generated snapshots, full physical/derivative/text/site charging, upload idempotency keys and orphan reconciliation remain incomplete. An unconfirmed commit never licenses unlinking possibly committed data; inspect the retained state before retrying.

## Generated snapshots and durable storage publication

Published board snapshots now join original-byte admission under the same user lock and include pending upload bytes. This supersedes the prior upload-only writer limitation: both current Asset creation paths participate in the environment-controlled original-byte allowance. Existing snapshot retries retain their current destination-read check. Session validity is checked after render/storage and just before commit; a slow operation cannot rely only on its initial authentication. Snapshot commit uncertainty follows the same conservative file-retention principle as uploads. This is not full logical/physical accounting, new proposed-policy enforcement or a general membership-lock redesign.

Schema 0011 indexes originals by contributor. Storage publication fsyncs newly created directory ancestry as well as the file/shard and refuses to clobber existing objects. Six focused snapshot/storage tests cover tiny quota, active pending uploads, lost/unknown commit replies, expiry during storage and actual directory synchronization. Full validation passed **230 backend tests**, recovery/drift, **11 frontend tests** and production build. Final authority-guard additions also passed the 16 focused snapshot/upload regressions on a separately provisioned disposable database. Browser evidence passed **18 governance + 12 capability + 69 existing collaboration/touch + 2 operator-receipt checks** at root/prefix; no hosted-CI completion is claimed. The development and research instances were migrated to head 0011 and preserve their synthetic content.

P5.1 remains incomplete: complete canonical text/board/derivative/site accounting, durable reconciliation/repair authority and broader capability workflows are outstanding. ## Upload request receipts and replay

Schema 0012 adds optional owner-scoped upload keys bound to measured bytes and submitted metadata. Pending receipt/reservation creation is durable before storage; completion, Asset insertion and reservation removal are atomic. Identical completed requests return the original file without extra bytes or quota charges. Conflicting intent, pending work, failed/expired attempts and deleted results have distinct stable errors. Owner-only status rechecks current content access; administrators, siblings and board-only sessions cannot use receipts as an access grant. Request identity expires after 24 hours, with lazy per-user cleanup on subsequent admission. Restore invalidates copied attempts alongside reservations.

Independent review reproduced a cleanup deadlock caused by receipt and expired-reservation lock inversion. Failure release now serializes through the same user row before locking the reservation/receipt, without requiring the failed worker's session to remain valid. A concurrent regression pauses failure release with its receipt locked, waits until PostgreSQL confirms another admission is blocked, then verifies both finish. User deactivation/revocation still cannot block necessary cleanup solely because authorization expired.

Validation: **250 backend tests**, real PostgreSQL recovery, migration drift, **11 frontend tests**, typecheck and production build passed serially. The hardened 20-test receipt suite also passed after adding the explicit blocked-backend check. **20 Chromium/nginx checks** passed at root/prefix, deliberately losing the first committed response, checking status and replaying the same key with single charging, followed by changed-content and revoked-access denials. Independent review ran the concurrency regression in separate disposable databases: injecting the old cleanup implementation failed with a PostgreSQL deadlock; the corrected implementation passed. No remaining high-impact backend finding; hosted CI completion is not claimed. Development/research instances were migrated to head 0012 and restarted with their synthetic data preserved; readiness, login, usage and receipt-route checks passed on both.

This slice is the backend/API contract; existing file pickers do not yet retain request keys or provide a closed-tab recovery interface. Next: integrate those controls and continue complete P5.1 accounting/reconciliation; portable archives and retention remain dependent future phases.

## File-picker recovery controls

The noticeboard and desktop board now retain bounded, in-memory upload attempts with a request key and the exact selected File. Users explicitly check a receipt or retry the same request; there is no automatic write retry. Pending attachments block posting, board images serialize through one unresolved attempt, and failed/expired/inaccessible results cannot silently start over. Already-used assets are not placed/attached again. The client stops retrying before the server's 24-hour identity window ends. Dismissing does not delete a stored file. Navigation, reload and sign-out discard these in-memory controls; persistent recovery remains future work.

Independent review caught a truncated-success-body case: headers may arrive after commit while JSON parsing fails. The transport now reports an uncertain response rather than a parser error or false success; same-key recovery remains available. **31 frontend tests**, typecheck and build passed. **24 Chromium root/prefix checks** passed across actual noticeboard and board inputs, post-commit response loss/truncation, current-view check/retry, single charging, durable attachments and mobile controls. [Screenshots](evidence/upload-recovery/README.md) were visually inspected. The existing collaboration/touch browser suite also passed **69/69** checks at root/prefix. Its first launch found no Playwright-managed browser; the harness now accepts LABADDA_CHROMIUM and passed with the installed Chromium. Backend code/schema are unchanged in this slice, so the previous 250-test backend baseline was not rerun for this frontend-only change.
