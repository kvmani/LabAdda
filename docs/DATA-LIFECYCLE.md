# Data lifecycle, quotas and retention — future implementation contract

Status: **normative P5 requirements**, 2026-11-08. Partial implemented foundations are tracked in [P5-PROGRESS.md](P5-PROGRESS.md); the full lifecycle contract is not implemented. This is the normative extension of S2–S4 for P5. Requirements use MUST for release gates and SHOULD for defaults that may change only with recorded justification. [Archive format](ARCHIVE-FORMAT.md), [admin console](ADMIN-CONSOLE.md) and the acceptance matrix in TESTING.md are part of this contract. Existing pilot configuration remains unchanged until a tested migration activates the new policy engine.

## Purpose and boundaries

**DL-01.** LabAdda is a lightweight collaboration and quick-sharing service, not a large-dataset repository or permanent records store. Ordinary small-file exchanges must remain fast. Users must see limits, expiry and recovery choices before committing content; policy enforcement must not silently discard accepted work. Large datasets should use an approved internal repository/link, without external fetching or previews.

**DL-02.** Distinguish four operations in every UI/API:

| Operation | Meaning | Server storage effect |
| --- | --- | --- |
| Freeze workspace | Existing archived-workspace flag: stop shared writes, retain authorized reads | Frees no space and does not suspend retention |
| Download archive | Authorized content copy to the user's device | Does not delete or uncharge originals; generated export is temporary |
| View uploaded archive | Isolated, read-only, temporary view of a portable archive | Consumes bounded staging/viewer quota until cleanup |
| Materialize selected archive items | Explicitly create new content in a selected writable destination | Consumes current destination/user quotas; never restores source grants |

Disaster recovery remains an operator-only database-and-assets operation governed by RECOVERY.md. User archives must contain no database dumps, executable restore scripts, credentials or sessions. A backup is not a promise that a user-deleted item remains downloadable.

## Policy model and initial profile

**DL-03.** All product policy fields below must be configurable in the admin web console, persisted as versioned database policy, auditable and discoverable through an effective-policy API. Environment settings supply bootstrap defaults and immutable operator safety ceilings only; they must not silently override web policy. The console must display such ceilings and explain when a change needs a host operator. Credentials, filesystem destinations, certificate keys and OS configuration are not ordinary web-editable policy fields.

**DL-04.** Policies have stable IDs, schema version, monotonically increasing revision, scope, proposer, reviewer when required, reason, created/effective timestamps and optional expiry. A saved draft does not activate policy. Every effective value must resolve to its source revision. Unknown fields, missing units, negative values, NaN, overflow and incompatible schema versions must fail validation. Zero is never an implicit unlimited/disabled sentinel: use explicit states `finite`, `disabled` or `unlimited`, subject to site ceilings.

**DL-05.** The global per-user attributable-content limit resolves from the site user default plus an explicit user exception only; home unit, membership changes or choosing a different destination cannot change that global allowance. Workspace-specific fields resolve deterministically: site default → nearest organizational override along the immutable-ID ancestry path → exact workspace override; explicit per-user exceptions apply to user limits only. Projects and collaborative groups use site defaults plus their own exact overrides, never inferred parent-unit policies. Each override declares whether descendants may relax it and the maximum relaxation; a locked site constraint always wins. Admission must satisfy **all** applicable user, workspace, explicit subtree and site budgets. The UI must show the winning value, inherited constraints and why a proposed exception is refused. Reparenting is a policy change requiring an impact preview. Conflicting holds/expiry rules must resolve according to DL-16, not list iteration order.

The following is a **proposed lightweight starting profile**, not an automatically activated site decision:

| Field | Proposed value | Required semantics |
| --- | --- | --- |
| File size / attachments per post | 20 MiB / 5 | Preserve current pilot defaults; configurable per approved file class |
| User attributable live content | 500 MiB | Includes provisional uploads and attributable shared content |
| Workspace live content | 2 GiB | Direct workspace content; subtree totals reported separately |
| Site managed-data budget | Operator provisioned; explicitly confirmed in UI | No guessed production capacity and no automatic unlimited setting |
| Warnings | 70%, 85%, 95%; hard admission at 100% | Numeric remaining bytes, trend, next actions; hysteresis/deduplication |
| Upload burst / daily uploaded originals | 60 files/hour / 250 MiB per rolling 24 hours per user | Separate from live quota; reservations prevent parallel bypass |
| Concurrent transfer jobs | 2 per user, 4 per site | Separate bounded worker pools; ordinary UI requests retain capacity |
| Export / archive upload | 250 MiB per package, 1 GiB expanded | Split large exports into independently valid packages; hard safety ceilings |
| Temporary archive view / export download | 24 hours / 24 hours after completion | Optional shorter values; show exact expiry; no perpetual cache |
| Filesystem reserve | max(2 GiB, 10% of the managed filesystem) | Admission also checks actual free space, DB/log/temp growth and inodes |
| Retention evaluator | Hourly, bounded batches | Retryable jobs; expose lag rather than pretending schedules are exact |
| Warning lead / reversible removal window | 14 days / 7 days | Required notice before newly scheduled destructive changes |

**DL-06.** The admin must be able to adjust size/count limits, quota classes, user exceptions, workspace/subtree budgets, allowed media types, transfer rates, concurrent jobs, warning thresholds, retention/notice/grace periods, trash, archive-view TTLs, import/export bounds and worker schedules through the reviewed policy flow. Product-supported media types are an explicit allowlist: a policy change cannot enable a renderer that has not been implemented and security-tested. Raw SVG remains blocked until a separately reviewed capability exists. Generated SVG archive figures are a different, controlled renderer.

## Accounting, admission and user experience

**DL-07.** Maintain durable accounting for original bytes, derivatives, text/board logical bytes, object counts, reservations, provisional data, trash, temporary exports/imports and system overhead. User/workspace **logical charges** and site **physical usage** are separate measurements. Shared bytes may count toward both user and workspace limits, but physical site totals must count a stored blob once. A deduplicated blob must not provide a cross-scope existence/timing oracle. Account for thumbnails, snapshots, DB/index growth and compaction explicitly; text/board charges use a versioned canonical UTF-8 serialization rule, not browser character counts or a fictitious zero cost. DB physical size must be measured separately from logical attribution.

**DL-08.** Provisional uploads charge the uploading user and staging pool. On durable attachment/board commit, transition the reservation atomically to the destination workspace and the attributable user; do not charge provisional and committed states twice. Shared contributions remain attributed to their stable contributor ID after departure/deactivation. Admins may transfer **shared-content accounting responsibility**, with preview and audit, to an approved workspace service budget or responsible owner; this grants no content access, rewrites no authorship and cannot transfer another user's personal notes. Freeing user quota must never delete colleagues' still-referenced files. Destination-owned published copies are independent logical charges and retention units.

**DL-09.** Admission is reserve → validate/store → commit or release. Concurrent uploads, retries, attachment commits, snapshots and archive materialization must use transactional counters/reservations and idempotency keys. A reservation has an expiry and bounded cleanup; an incomplete file never becomes publicly readable. Multipart declared lengths are untrusted: enforce measured streaming bytes, decompression limits and final committed charges. Retries charge once. A crash reconciler must repair orphan/reservation mismatches without deleting referenced content. Byte counters must use integers with checked arithmetic.

**DL-10.** At/over a quota, users retain authorized reads, deletion/cleanup and downloads. Block growth operations with a stable reason, affected scope, current usage, limit, required/free bytes, reservation expiry and permitted actions. Distinguish user/workspace/site quota, rate limiting, disk reserve and temporary outage; use `413`, `429` with `Retry-After`, or a documented quota/storage error as appropriate, never a false permission error. Keep unsent text locally within an explicit size/privacy bound, offer copy/download, and never show Saved for refused writes. Small text exchanges may use a configured reserved collaboration budget after file-upload admission closes; its limits and exhaustion must be visible, not an unlimited bypass.

**DL-11.** Lowering a quota below existing usage does not remove data. Show all newly over-limit accounts/spaces, notify owners, allow a configured transition period, and then block additional growth as previewed. Expiring exceptions revert through the same forecast/notification process. Downloading an archive does not free quota. Trash frees active-write allowance only if policy says so, while physical capacity is credited only after reference-safe purge; the console and user UI must show both. Daily upload limits do not reset on deletion, logout, account deactivation or re-import.

**DL-12.** The user's Usage and archives page must show attributable usage by scope/type, live vs trash vs temporary bytes, active reservations, effective policies, next expiry, upcoming deletion, pending downloads and actionable suggestions. Offer largest/oldest eligible items, archive selection by date/type/workspace and a request for a temporary exception with reason. Users may inspect only metadata within their own grants. The default experience should support a small document handoff with no administrative interaction when capacity is available. Emergency read/export/cleanup must remain usable with bounded streamed output when free disk is low; do not require building a second full server copy just to evacuate content.

## Retention clocks and lifecycle

**DL-13.** Expiry uses UTC instants and immutable server timestamps; display the site's chosen IANA time zone, exact local deadline and UTC equivalent in policy previews. New installs start with retention **observation only**. The following finite profile may be proposed for site review, but cannot delete existing or new content until activated with DL-18 and the admin safeguards:

| Class | Proposed active lifetime | Clock / dependency rule |
| --- | --- | --- |
| Chat message | 180 days | Individual server commit time; thread activity and edits do not renew it |
| Notice / reply | 365 days | Individual commit time; expiring a parent retains a content-free placeholder if permitted descendants survive |
| Attachment / embedded image | Inherit owning item by default; optional explicit finite file-class lifetime | A shorter file lifetime requires the reviewed reference-transition behavior in DL-15; retained/held dependencies can block physical purge |
| Current live board state | No age-based purge in the initial profile | Keep current objects; compact history, never erase visible state as routine compaction |
| Board replay/history | Minimum replay/undo contract from S3; optional longer reviewed policy | Durable snapshot plus retained operations must reconstruct current state; retain exports/published copies independently |
| Personal notes | No automatic expiry in initial profile | User-managed; an admin proposal for finite expiry requires the same explicit notice/grace process |
| Frozen workspace | Same per-class clocks | Freeze is neither a hold nor permanent archival storage |
| Uncommitted upload / finished temporary archive jobs | 24 hours | Server creation/completion time, bounded cleanup |
| Operational logs / usage aggregates | 30 days detailed / 365 days aggregated | Configurable separately; no content in telemetry |
| Restricted security/policy audit | 365 days minimum proposed floor | Never deleted by ordinary user-content cleanup; site review may require longer |

Temporary upload/export/view TTLs are disclosed at creation and do not require a 14-day advance notice; that notice default applies to durable-content expiry and newly shortened destructive policies. No grace window may exceed its governing safety/capacity constraint without an explicit reviewed exception.

**DL-14.** Lifecycle states are `active → expiry_notice → trash → purge_pending → purged`; preservation holds are orthogonal and visible only to authorized roles. A user-initiated removal must hide content immediately from ordinary delivery but respect restore windows, references and holds. An expired original must disappear from fetch, search, reminders, previews, notifications, sockets and queued jobs consistently. Content-free tombstones must not retain the body, filename, private scope label or other forbidden metadata after payload purge. User restore within grace rechecks current permissions, quota and policy; it grants no fresh retention term by stealth.

**DL-15.** Before purge, evaluate the complete reference graph: post/reply attachments, provisional uploads, board epochs/ops/snapshots, published copies, job snapshots and retained trash. An explicit file-class lifetime may expire an attachment before its post: the approved plan must transition every affected live link to a clearly displayed content-free expired-attachment placeholder, notify the affected audience/owner, and preserve surviving post text. A shorter embedded-image policy must similarly make the board representation explicit and keep reconstruction valid; it cannot silently break a retained snapshot. Any unplanned or held dependency that still requires the bytes blocks physical purge. Independently owned published copies keep their own policy and references. Purge must be idempotent, bounded, resumable and safe across crash/restart and concurrent edits. Mark durable intent, prevent new references to a purging object, then remove payload and reconcile meters. Never unlink a blob solely because one referencing row expired. Cancellation after an irreversible unlink must be reported as too late. Board history compaction must preserve current state and the advertised replay/undo window; tests must cover embedded-image retention across compaction. Retry queues cannot deliver an expired payload.

**DL-16.** A preservation hold, explicit paused lifecycle job, or a required unverified recovery prerequisite wins over automatic purge. Holds require reason, scope, owner, review deadline and audited creation/removal. Show retained bytes, quota implications and blocked purge; do not silently reclaim held bytes or allow unlimited unmetered held storage. Escalate capacity shortfalls to administrators. Content-hold administration is metadata-only; access to a private note body remains denied. Removing a hold must produce a fresh impact preview and notice period before overdue deletion. Moving workspaces or disabling users never erases or silently changes these protections.

**DL-17.** Retention changes apply prospectively by default. Applying a shorter lifetime to existing content is a separately reviewed retroactive action. Editing a message, touching a workspace, downloading a file, freezing/unfreezing a group, retrying a request or moving a file must not reset the clock. Explain whether a replacement file is a new item or a revision and retain lineage. A source-aware materialization cannot erase known expiry/history to evade policy; viewing an old archive remains possible in the temporary viewer without republishing it. A deliberate new publication uses a newly evaluated policy and explicit audience/lineage rather than claiming to restore the original item unmodified.

**DL-18.** Automatic purge requires: complete accounting/reference reconciliation; a bounded dry run covering the proposed population; fresh policy/data-generation approval; user/owner notifications; expiry and restore windows; and a recorded verified recovery point when the action requires it. Job preflight must verify available reserve and recovery freshness, not merely accept an unchecked checkbox. Time advancing past a notice deadline is not consent to broaden an approved deletion set. Runs may process only their immutable approved candidate IDs, and must recheck each candidate's current version, permissions, holds and references. Scheduled observation may generate new plans, never extend an existing plan. A human may approve one complete plan executed in bounded chunks; retries use the same candidates. Changed candidates are skipped and reported; additional candidates need a new plan. Observation-only jobs may count candidates but must write no lifecycle mutations.

For prospective unattended retention, an admin may explicitly approve a **bounded standing authorization**, distinct from a one-time candidate plan: fixed policy revision and immutable scope IDs, content admitted after activation with expiry disclosed at creation, permitted classes/actions, notice/grace requirements, maximum items/bytes per run and rolling day, required inventory/recovery freshness and a finite review/expiry date (proposed 90 days). Each run first freezes an exact candidate plan and records its delegated authorization and checks; it cannot add IDs while executing. Any exceeded envelope, stale observation, changed policy/holds/grants, recovery gap or expiry pauses the job for review. Existing-content retroactive deletion, removal of holds and widened scope always require a fresh human-reviewed candidate plan; standing authorization cannot approve them. Changing the envelope requires another policy dry run/review. No perpetual unbounded deletion grant or silent service self-approval is permitted.

## Archive download, viewing and selected re-import

**DL-19.** Users may export selected currently readable items, their own notes, date ranges or a whole readable workspace, within policy. Default selection must state whether it includes colleagues' content and attachments. Stewardship may permit workspace-wide export only for readable workspace content; admin privilege alone never grants export of bodies. Export at a stable logical snapshot, recording cutoff/revisions and intentional exclusions. Selection, queue admission, worker execution and every download/range request recheck active identity, grants and lifecycle. Active streams must subscribe to revocation/expiry and recheck permission at bounded chunks and before each application write; the initial target is cancellation within 1 second of a committed revocation. The implementation must document its transport buffering boundary, stop writing further protected chunks once revocation is observed, and close the stream. Already written/in-flight bytes cannot be recalled; the UI and tests must not promise instant network erasure. On revocation or expiry, cancel inaccessible work, invalidate links and remove undelivered artifacts; already downloaded bytes cannot be recalled. Default authenticated, expiring downloads; no permanent bearer URLs or public caches.

**DL-20.** Provide both a human-readable offline view and a machine-readable package conforming to ARCHIVE-FORMAT.md. Export completion means the package was generated and verified, not that the user stored or backed it up. Show size, digest, expiry and selection manifest. Resumable range downloads may be supported with the same authorization checks. Split packages must each open independently and explicitly report cross-part relationships/omissions. A request to delete after export is a distinct, previewed action and may not use mere job success/download-start as evidence of archival safety.

**DL-21.** Uploaded archives enter private quarantine with separate compressed/expanded/member-count/time budgets. Offer inspect → read-only temporary view → optionally select materialization destination → dry run → confirm. The default viewer shows original source/scope labels as historical metadata, not live access or endorsement. Imported attachments remain protected; no automatic external requests, active SVG, HTML scripts, plugins or macro execution. A server archive upload is data, never an executable restore request. View/download rechecks current viewer ownership/authorization; TTL cleanup invalidates all links and releases bytes.

**DL-22.** Materialization requires current destination write permission and explicit audience confirmation. A private-note archive defaults to the **currently authenticated importing user's own private space**, never the account claimed as author inside the package; publishing anything to colleagues requires a separate explicit destination choice. Foreign/missing source identities never create accounts, memberships or trusted authorship. Source IDs are namespaced; map to new IDs and keep provenance. Duplicate imports must not silently duplicate data, overwrite current items or re-send reminders. Show a dependency/conflict plan; a repeated idempotency key returns the original result. Imports must be atomic per declared unit or expose precise partial outcomes and safe retry; failed units stay invisible and release reservations. No blind database merge, automatic session restoration or imported admin role.

**DL-23.** Archive viewing and materialization use the service's reservation, rate/concurrency and physical-capacity admission controls, with bounded staging. Temporary exports/viewers charge explicit per-user transfer/staging pools, not a second live-content charge for the originals. Reaching a live-content quota must not by itself prevent download or a permitted temporary read-only archive view; export may use bounded streaming instead of a temporary full copy. Materialization consumes ordinary live user/workspace budgets. Exhausted staging/rate/physical capacity still produces an honest retry or cleanup action, not an unbounded bypass. Present quota/expiry effects before execution and prevent archive loops from bypassing user or site limits. Offline unsigned archives may be safely viewed as untrusted data after structural validation; trusting embedded identity, timestamps, policy exceptions or holds requires independently trusted provenance and never overrides current permissions. A known item from this site retains its lineage and any applicable holds/tombstones. Deletion of a server copy does not promise deletion of off-device copies.

## Jobs, audit and recovery interaction

**DL-24.** All asynchronous work has a durable job ID, idempotency key, requester/scope, effective policy revision, selection/plan digest, stage, progress, byte/item counts, timestamps, heartbeat, cancellation boundary and sanitized structured failure. State transitions are `queued → preflight → running → verifying → completed`, with `paused`, `cancelled`, `failed`, and explicit partial outcomes. Leases and checkpoints must prevent duplicate execution after crashes. Revalidate access/policy at execution boundaries. Admin retry buttons create accountable attempts rather than resetting history or launching concurrent destructive workers.

**DL-25.** Record policy changes, privileged accounting adjustments, archive jobs, holds, lifecycle transitions, import mappings, exceptions and purge outcomes in the restricted audit trail. Do not copy message bodies, private notes, credentials or attachment contents into audit/logs. Operational errors must carry stable codes, correlation IDs and recovery guidance. Audit writes and critical failure records require reserved capacity and fail-safe behavior; an unavailable audit sink must prevent irreversible policy activation/purge, not silently bypass it.

**DL-26.** A recovery restore must restore policy revisions, holds, metering/reservation intent and job checkpoints consistently, invalidate sessions, and pause imported in-flight lifecycle/import/export jobs. Reconcile counters and current time before exposure. Overdue data must not be bulk-purged immediately on restart; require a fresh approved plan and notice handling. Backups have a separate restricted retention policy and verified restore history. UI labels must state when deleted live content may still exist in protected backups and the scheduled backup expiry; recovery must reapply recorded deletion intent/holds before serving restored content. Maintain a protected append-only lifecycle-intent ledger independently of application backups, with an off-instance retained copy, monotonic sequence/checkpoints, integrity/authenticity verification and no content bodies. Record deletion intent/tombstones, preservation holds and relevant policy-authority revisions durably **before** irreversible action; a missing ledger acknowledgement blocks that action. Every backup identifies its ledger checkpoint. Restore must prove a continuous verified suffix through the agreed recovery boundary, reconcile it idempotently, and document any gap or unavailable authority. This ledger has separate reviewed retention at least as long as supported backup recovery, privacy controls and tested recovery; a counter inside the same old dump is insufficient. If history since the backup cannot be verified, keep the restored instance isolated pending explicit operator reconciliation, rather than resurrecting data to users or inventing a complete history.

## Nonfunctional and delivery rules

**DL-27.** All controls work beneath root or configured URL prefixes, without public network or external telemetry, and with accessible forms, keyboard operations, text status, explicit units and time zones. Long jobs must not block the API loop or drawing fanout. Initial measured acceptance targets on the representative VM: usage pages p95 <1 s from bounded aggregates; ordinary admitted small-upload commit adds <200 ms p95 quota overhead excluding transfer/scan time; background lifecycle/export jobs add <10% regression to the S4 interaction latency under the agreed workload. Record hardware, workload and measurement method. These are future qualification targets, not existing performance claims.

**DL-28.** Roll out schema/meters and read-only observability first, then authorized exports/offline viewing, quota warning mode, reviewed enforcement, retention observation and finally bounded deletion. Import/materialization follows verified package validation and quota enforcement. Existing content is backfilled and reconciled before any hard limit or deletion. Migration discrepancies block activation and expose an actionable reconciliation report. Every slice updates API schemas, operator/user instructions, acceptance evidence and the roadmap. Feature flags and rollback must preserve accounting and previously accepted content; never downgrade a schema by dropping lifecycle/provenance history.
