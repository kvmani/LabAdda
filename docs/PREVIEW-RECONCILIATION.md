# Historical preview metadata reconciliation

This trusted-host operator tool fills missing expected preview length/hash metadata. It **never rewrites or deletes files**, changes authorship/access, activates policy or changes original-only pilot quota admission. There is no web apply action. The admin/operational receipt API grants no additional content rights.

An existing preview is eligible only when its original matches the database's expected length and SHA-256, regeneration with the current sanitized PNG recipe succeeds, and the regenerated bytes exactly equal the existing preview. A missing, corrupt, oversized, unsafe or different preview remains unknown with an issue; it is not silently repaired or blessed. A different Pillow/renderer output may therefore require a separate future repair procedure.

## Dry run

Use the normal instance settings and private asset directory. No metadata changes occur by default:

```bash
labadda reconcile-previews --max-assets 100 --max-bytes 104857600 --max-seconds 30
```

The JSON result includes a durable receipt ID, candidate/issue counts, bounded diagnostic codes and `plan_digest`. It contains no filenames, storage paths or individual content hashes. Read the complete result before application. A live dry run can race other writers and is not a consistent inventory or site-health assertion.

## Reviewed application

Stop **all application, scheduler and maintenance writers** using the deployment's maintenance procedure. Create/review a final dry run against that stopped instance. Use the same budgets and cursor when applying its digest:

```bash
labadda reconcile-previews --max-assets 100 --max-bytes 104857600 --max-seconds 30 \
  --apply --writers-quiesced --expected-plan 'DIGEST_FROM_DRY_RUN'
```

Replace the quoted placeholder with the exact returned 64-character lowercase digest. `--writers-quiesced` attests an operator action; the tool does not stop or independently verify every writer. Apply locks the selected Asset rows and serializes other applications of this tool, repeats verification and recomputes the plan. A changed selection, budget, cursor, source or eligible preview rejects the plan with **zero metadata updates**. Matching eligible rows, completion receipt and audit commit together. Audit failure rolls back updates. Skipped files remain unknown even in an otherwise completed batch; the CLI exits 2 when issues remain.

The digest is a content-bound confirmation, not an access credential or a general policy approval. Application requires trusted OS/database access. No HTTP endpoint accepts it.

## Batches and limits

- Default/max selection: 100/1,000 unknown-preview assets, ordered by immutable Asset ID. At most one extra row is selected to detect another batch.
- Default/max read budget: 100 MiB/1 GiB across originals and previews; a separate 32 MiB per-file limit is enforced before and during reads, including growing files.
- Default/max scan budget: 30/300 seconds. Checks are cooperative; blocking filesystem/database calls and image decoding do not have a hard wall-clock deadline. Database statements have a two-second timeout. Images are capped at 40 million pixels before full decode.
- `more_unknown_assets` describes only the bounded selection after the current cursor. If true, continue with `--after-asset 'NEXT_AFTER_ASSET_UUID'` using `next_after_asset` from the result. Include that same cursor for its apply. This permits walking past unrepairable files without pretending they were reconciled.
- A budget stop provides no applicable plan. Reduce batch size or adjust supported budgets, then dry-run again. Never interpret zero applied rows as proof of complete reconciliation.

After application, run `labadda inspect-storage` for an independent referenced-file check. `/usage` and operational views now count filled preview expectations as known; that metadata remains distinct from a current disk scan. Restart normal writers only under the existing deployment procedure. No recovery bundle or current release archive is automatically created by this tool.

## Receipts and interrupted work

Records appear with `scope: preview_metadata_reconciliation` in the existing protected inspection history. The web view distinguishes **Dry run** from **Apply**, candidate count, metadata-update count and stopped reasons. Ordinary file inspections retain their separate verification counts. Historical receipt schemas may omit newer fields and display Not reported.

An interrupted worker can leave a running receipt. If the final commit reply is lost, a fresh completed receipt can confirm success; otherwise the CLI reports an unconfirmed outcome and leaves durable state for inspection. Inspect the receipt and current metadata before attempting another plan. No uncertain result licenses deletion or alteration of stored bytes.

This closes one narrow historical-derivative gap. Complete site/physical/text/board accounting, generalized reconciliation/repair capability, policy activation, archive export and retention remain future gates.
